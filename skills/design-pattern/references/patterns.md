# Game Programming Patterns — Core Prompt Catalog

Each entry below is a self-contained **core prompt**: a lens for recognizing the pattern in a real codebase and explaining how it resolves the problem. Use the **Recognize the need** signals to confirm a pattern applies, **Why it works** to justify it, and **Application sketch** to plan the change. Always weigh **Keep in mind** before recommending — every pattern has a cost.

Patterns are grouped by the book's five categories. Source: Robert Nystrom, *Game Programming Patterns*.

---

## Design Patterns Revisited

Classic Gang-of-Four patterns, reframed for games (and general software).

### Command
- **Intent**: Encapsulate a request as an object — a reified method call wrapped in data you can store, pass, queue, delay, or reverse.
- **Recognize the need**: Raw input handling that hard-wires button presses directly to functions like `jump()` and `fireGun()`, making bindings unconfigurable; an interface with a single method that returns nothing; tight coupling where commands implicitly find "the player" instead of being passed a target actor; a need to queue, log, or stream a series of actions (AI emitting commands, network replay); a need for undo/redo that is "surprisingly hard" without encapsulation; a desire to let the player or AI drive any actor by swapping the execution target.
- **Why it works**: Wrapping a method call in an object introduces indirection between the producer of the call and the consumer. The call becomes first-class data, so it can be stored in a variable, handed to a dispatcher, delayed until the right actor is known, serialized over the network, or reversed. Decoupling producer from consumer is what enables reconfiguration, AI/actor swaps, and undo.
- **When to use**: Configuring/remapping user input; decoupling AI command selection from the actor that performs it; undo/redo in level editors and turn-based games; replay systems that record per-frame command streams; networked multiplayer where commands are serialized and replayed remotely. Most large programs end up using it somewhere.
- **Keep in mind**: In languages with real closures or first-class functions, prefer them — Command is partly a way to emulate closures. Actual classes are still worthwhile when a command has multiple operations (e.g., `undo()`) or fields whose contents you want visible. In non-GC languages, the dispatcher owns freeing command memory. One-use commands (created per move, bound to a specific instance) differ from reusable command objects held by the input handler. Undo requires discipline: every state mutation must route through a command. Memento is tempting but usually wastes memory; store only the bits you change.
- **Application sketch**: Define a base `Command` with an `execute()` method; subclass per action. For actor independence, pass the `GameActor` into `execute()` so one command can drive any character. Have `handleInput()` *return* a command rather than executing it, then run it on the chosen actor. For undo, add an `undo()` method, store before-state in the command (e.g., `xBefore_`, `yBefore_`), and keep a list of commands with a "current" pointer — undo moves back, redo moves forward, a new command after undo discards the tail.

### Flyweight
- **Intent**: Make a multitude of objects lightweight by splitting shared intrinsic (context-free) state from per-instance extrinsic state, sharing one copy of the intrinsic state across all instances.
- **Recognize the need**: Thousands or millions of similar objects (a forest of trees) whose combined data is too large for memory or the CPU-to-GPU bus; large blobs (meshes, textures) duplicated identically across every instance; a parallel urge to model terrain as an enum plus `switch` statements that smear one terrain type's data across many methods; wanting the encapsulation of real objects without paying for an instance per tile; stateless chunks of pure behavior where multiple equivalent instances waste memory.
- **Why it works**: Pull the data all instances share into a single shared object and give each instance only its unique data plus a reference to the shared one. Because the shared object carries no instance-specific state, every instance can point to it without affecting visible behavior — provided it stays immutable. This collapses memory and bus traffic (the GPU can receive shared data once and instance parameters separately via instanced rendering) while preserving an object-oriented API.
- **When to use**: When you have too many objects and most of their data is shared/common. If you find yourself creating an enum and doing lots of switches on it, consider Flyweight instead. Don't dismiss it on performance grounds — profile first; flyweights can actually be faster than enums, though it depends on memory layout.
- **Keep in mind**: Flyweight objects are almost always immutable — mutating one changes behavior across every reference simultaneously, breaking the invisibility of the optimization. Pointer indirection can cause cache misses (see Data Locality), so profile before assuming. If you can't predict which flyweights are needed, create them on demand via Factory Method and store them in an Object Pool. State-pattern state objects with no machine-specific fields are natural flyweights. Differs from Type Object in intent: Type Object lifts "types" into the object model; Flyweight is purely about efficiency.
- **Application sketch**: Identify the intrinsic state (mesh, textures, movement cost, isWater, texture) and extract it into a separate class (`TreeModel`, `Terrain`) with `const`/immutable methods. Each instance (`Tree`, world tile) keeps only extrinsic state (position, scale, tint) plus a pointer to the shared object. Store shared instances directly in the world/container and have instances reference them — a pointer is often no larger than an enum. For rendering, push intrinsic data once and the per-instance parameter list separately, using instanced rendering so a single draw call renders the whole forest.

### Observer
- **Intent**: Let one piece of code announce that something interesting happened without caring who receives the notification, decoupling the subject from its observers.
- **Recognize the need**: A system like physics needs to trigger behavior in an unrelated system like achievements without coupling them; "tendrils" of one concern (e.g., `unlockFallOffBridge()`) twining through unrelated code (collision resolution); wanting to change or tear out the dependent system without touching the event source; multiple independent systems needing to react to the same event (achievements *and* audio on a fall); a subject that supports only a single observer causing observers to silently unregister each other.
- **Why it works**: The subject holds a list of observer pointers and exposes public `addObserver()`/`removeObserver()` while calling a generic `onNotify()` on each. It communicates with observers without being statically coupled to them, and using a *list* (not a single observer) keeps observers from implicitly interfering with each other — each behaves as though it alone is watching. Sending a notification is just walking a list and calling virtual methods: synchronous, with no per-send allocation.
- **When to use**: When two mostly unrelated "lumps" of code (achievements and physics, likely owned by different people) need to talk without merging into one lump, and the bare minimum of communication is desired. Do *not* use it within a single feature lump where you often need to reason about both sides of the communication at once — prefer something more explicit there. Fits best outside hot code paths.
- **Keep in mind**: It is synchronous — a slow observer blocks the subject ("stay off the UI thread"); push slow work to another thread or queue. Destroying observers/subjects leaves dangling pointers; observers must unregister themselves (the *lapsed listener problem*: even with GC, subjects retain references and keep zombie observers alive, wasting CPU). Reasoning across an observer chain is hard because communication is dynamic, not statically traceable. Mixing observers with threads and locks can deadlock — consider Event Queue for highly threaded engines. The class-based interface is heavyweight and rigid (a single `onNotify()` can't distinguish subjects without help); a modern design uses function/closure-based observers instead.
- **Application sketch**: Define an `Observer` interface with `onNotify(subject, event)` (parameters up to you; generics/templates fine). The `Subject` owns a list of observer pointers, public `addObserver()`/`removeObserver()`, and a protected `notify()` that walks the list. Subjects call `notify()` at noteworthy points. To avoid dynamic allocation, thread the list *through* the observers themselves (intrusive linked list: each `Observer` carries a `next_` pointer) at the cost of one-observer-per-subject, or use a pre-allocated Object Pool of separate list-node objects for many-to-many without allocation. Prefer composition (a separate "event" object the subject holds) over inheriting `Subject`.

### Prototype
- **Intent**: Let an object spawn other objects similar to itself by cloning a prototypal instance — copying both class and configured state.
- **Recognize the need**: A parallel class hierarchy (a `Spawner` subclass per `Monster` subclass) generating lots of classes, boilerplate, and duplication; the need to spawn variants (fast ghosts, weak ghosts) from a template rather than just by class; in data modeling, sibling JSON entities (goblin grunt/wizard/archer) repeating identical fields (health, resists, weaknesses); one-off special entities (bosses, unique items like the "Sword of Head-Detaching") that are refinements of a common object.
- **Why it works**: Give the base class an abstract `clone()` returning a new object of the same class and state; a single spawner holds a prototype and stamps out copies, collapsing the parallel hierarchy into one spawner class. Because state is cloned too, one prototype can produce many configured variants. For data, declaring a `"prototype"` field lets an object delegate missing properties to another object via single delegation, eliminating duplication without an abstract base.
- **When to use**: The `clone()` *design pattern* is rarely the best answer in class-based languages — spawn functions, C++ templates, or first-class types in dynamic languages usually fit better. Prototypal *delegation*, however, is genuinely useful for data modeling with lots of little variations and one-off special entities. Pure prototype-based *languages* (Self) are elegant but tend to produce "mushy" code harder to work with than classes.
- **Keep in mind**: The `clone()` approach still requires implementing `clone()` in every class — about as much code as the spawners it replaces — and has nasty semantic ratholes (deep vs. shallow clone: does cloning a demon clone its pitchfork?). Big class hierarchies are themselves a pain; modern engines use Component or Type Object instead. Doubling down on prototypes tends to make code harder to wrap your head around.
- **Application sketch**: For the design pattern: add a virtual `clone()` to the base class returning a new same-class same-state instance; define one `Spawner` that holds a prototype and calls `prototype->clone()` to spawn. Consider the alternatives first: spawn functions stored as function pointers, C++ templates parameterized by monster type, or passing the class itself in dynamic languages. For data modeling: let data objects declare a `"prototype"` field naming another object to delegate to; missing properties fall back to the prototype. Pick the simplest existing object as the delegation base rather than always manufacturing an abstract base.

### Singleton
- **Intent**: Ensure a class has one instance and provide a global point of access to it. (The book devotes this chapter to how *not* to use the pattern — Singleton is overused and usually does more harm than good.)
- **Recognize the need**: A class wrapping an external system with its own global state (e.g., a file-system API) that cannot behave correctly with more than one instance because concurrent operations must coordinate; many systems (logging, content loading, save state) all wanting convenient access to the same instance; "manager" classes (BulletManager, ParticleManager) that exist only to babysit other objects; wanting runtime/lazy initialization because static members can't use runtime config or depend on each other safely; wanting polymorphism through a subclassed single instance (cross-platform `FileSystem`).
- **Why it works**: A static `instance_` member plus a private constructor enforce a single instance at compile time; a public static `instance()` lazily creates it on first access and grants global reach. This superficially delivers single-instantiation, runtime initialization, and subclassability. But the book stresses the pattern solves *neither* underlying problem well — a singleton *is* global state, just wrapped in a class, and it inherits every drawback of a global.
- **When to use**: Sparingly — the GoF themselves stressed this and the message was lost on the game industry. The author has never used the full GoF implementation in a game. The legitimate pull is almost always *convenient access* (the second half of the GoF sentence), rarely both halves together; if single-instantiation is all you need, a plain static class is simpler.
- **Keep in mind**: It is a global variable — harder to reason about code (you must grep the whole codebase to find errant writes), encourages coupling (anyone can `#include` and grab it, compromising architecture), and is not concurrency-friendly (deadlocks, race conditions). It solves two problems when you usually have one: making `Log` a singleton locks you to a single logger forever, and later partitioning logs forces touching every call site. Lazy initialization steals your control — init cost (e.g., audio) can land mid-frame causing stutter, and you can't control heap layout or fragmentation. Most games abandon lazy init for a static instance, which is just a static class — at that point drop `instance()` and use static functions. Beware "manager" singletons; often the behavior belongs on the managed class itself.
- **Application sketch**: Prefer alternatives. (1) See if the class is needed at all — move "manager" behavior into the managed class. (2) To ensure single instantiation *without* global access, allow construction but `assert` on a second instance (runtime check). (3) For convenient access: pass the object as an argument (dependency injection); get it from a base class via a protected accessor (Subclass Sandbox); piggyback on an already-global `Game`/`World` object so only one class is global; or use a Service Locator. (4) If you truly need just single-instantiation, use a static class with `Foo::bar()` rather than `Foo::instance().bar()`. **Treat an existing Singleton as a smell to refactor away, not a pattern to introduce.**

### State
- **Intent**: Allow an object to alter its behavior when its internal state changes so that the object appears to change its class — implemented as a finite state machine.
- **Recognize the need**: A handful of Boolean flags (`isJumping_`, `isDucking_`) where some combinations are invalid (both true) — a strong hint you want an enum/state; every change to the input-handling code breaks something (complex branching plus mutable state is error-prone); an `enum` plus a growing `switch` on state with per-state data like `chargeTime_` smeared across the main class though only meaningful in one state; behavior that rigidly divides into a small number of distinct, mutually exclusive options; an entity that responds to a series of inputs/events over time and transitions between modes.
- **Why it works**: Model the entity as a finite state machine — a fixed set of states, one current state at a time, a sequence of inputs, and transitions. Replace flags/switches with a state interface (`handleInput()`, `update()`) and one class per state that owns both its behavior *and* its state-specific data; the main object holds a pointer to its current state, delegates to it, and swaps pointers to transition. This consolidates each state's code and data in one place and makes invalid combinations impossible.
- **When to use**: When an entity's behavior changes based on some internal state; that state can be rigidly divided into one of a relatively small number of distinct options; and the entity responds to a series of inputs or events over time. Common in game AI but also user input handling, menu navigation, text parsing, network protocols, and other asynchronous behavior. Do *not* use for complex AI — behavior trees and planning systems are the modern trend; FSMs aren't even Turing complete.
- **Keep in mind**: The constrained structure is both the FSM's greatest virtue and greatest flaw. Adding a second independent concern (carrying a gun) forces n×m states — fix with *concurrent state machines* (n+m) and accept some crude `if` coordination between them. Similar states with duplicated transitions call for *hierarchical state machines* (superstate/substate via inheritance or an explicit state stack). Plain FSMs have no memory of history — to return to a previous state use a *pushdown automaton* (a stack with push/pop). Static state instances save allocation but can't hold per-machine fields; instantiated states allow per-machine data but need careful allocation/freeing (don't delete `this` mid-method — return a new state and let the owner swap) and may cause fragmentation (Object Pool helps). Distinguish intent from Strategy (decouple behavior) and Type Object (share behavior) — State is about *changing* behavior by changing the delegate.
- **Application sketch**: (1) Define a state interface with a virtual method for each state-dependent behavior (`handleInput()`, `update()`). (2) For each state, a class implementing the interface; move each `case` from the old switch and any state-specific fields (e.g., `chargeTime_`) into it. (3) Give the main object a pointer to its current state and delegate; to transition, assign/swap the pointer. Use static instances for stateless states (a Flyweight) and instantiated states for stateful ones. Add `enter()`/`exit()` actions so each state owns its setup/teardown (e.g., setting the sprite) regardless of which state you came from. Scale up with concurrent state machines, hierarchical state machines (inheritance or state stack), or pushdown automata (stack with push/pop for history).

## Sequencing Patterns

Patterns about *when* things happen — time and order in a real-time system.

### Double Buffer
- **Intent**: Cause a series of sequential operations to appear instantaneous or simultaneous.
- **Recognize the need**: Visible "tearing" or flickering where a reader (e.g., video driver) sees a buffer half-written, displaying part old and part new state; state modified incrementally that the same code may access mid-modification by outside code or another thread/interrupt; the modifying code itself reads the same state it is mutating, so changes early in an update cascade into later parts of the same step (order-dependent behavior); wanting to prevent consuming code from seeing work-in-progress while readers read without waiting for writers; the system "looks visibly wrong" in the absence of buffering.
- **Why it works**: The class keeps two instances of the buffer — a *next* buffer that all writes go to and a *current* buffer that all reads come from. Because readers never touch the buffer being mutated, they always see a complete, consistent snapshot. When the writes are complete, an atomic *swap* exchanges the two buffers so the newly written one becomes publicly visible and the old one becomes the work area for the next cycle.
- **When to use**: When all of these are true: state is being modified incrementally; that same state may be accessed mid-modification; you want to prevent accessing code from seeing work in progress; and you want to read state without waiting for writes to finish. You'll generally know you need it because the absence of it looks visibly wrong.
- **Keep in mind**: The swap itself must be atomic (no access to either buffer during the swap) and must be faster than modifying the state — otherwise the pattern buys nothing. It requires two copies of the state in memory, costly on memory-constrained devices. With pointer/reference swapping, outside code cannot store persistent pointers into the buffer (it may point at the wrong buffer after a swap), and the buffer's existing data is from two frames ago, not the last frame — relevant if reusing prior-frame data (e.g., motion blur). Copying data between buffers (instead of swapping pointers) gives more recent prior-frame data but the swap can take significant time for large buffers. It is a low-level implementation pattern with few consequences for the rest of the codebase.
- **Application sketch**: Define a buffered class that encapsulates a buffer and holds two instances of it (next and current, often stored in a two-element array with `next_`/`current_` references indexing into it). Route all reads to `current_` and all writes to `next_`. Provide a `swap()` that exchanges the two references (or copies next into current) called once modification is complete. Decide the swap mechanism — swap pointers/references (fast, but no persistent pointers and stale two-frame-old data) versus copying data (newer prior data, but slower for large buffers). Decide granularity — a single monolithic buffer (simple single swap) versus per-object buffered fields (requires iterating all objects to swap, or use a shared static `current_` index offset so one static `swap()` flips every object at once).

### Game Loop
- **Intent**: Decouple the progression of game time from user input and processor speed.
- **Recognize the need**: The program blocks waiting for user input, so the game freezes when the player does nothing (animations halt, monsters stop attacking) — the event-loop model where the app sits idle until input arrives; game speed varies with hardware (too fast on fast machines, too slow on slow ones — the "turbo button" problem) because the loop cranks as fast as the CPU allows; gameplay slows down under heavy per-frame load (complex physics, many objects) because update and rendering are coupled to wall-clock frame time; needing the simulation to advance at a consistent rate across devices without knowing the target hardware in advance; needing the game to keep moving (animations, effects, AI) even with no user input.
- **Why it works**: The loop spins continuously, each turn calling `processInput()` (non-blocking — it handles whatever input has arrived since last call rather than waiting), `update()` (advancing the simulation one step), and `render()`. By measuring elapsed real time each frame and using it to drive how much game time to simulate, the loop decouples simulation cadence from both input arrival and CPU speed — gameplay stays consistent while rendering adapts to available horsepower.
- **When to use**: Essentially every game uses this pattern; if you're using an engine you won't write it yourself but it's still there. Even turn-based games need it because their visual and audible states (animation, music) keep running while waiting for the player's turn. The distinction between an "engine" (owns the loop, calls into your code) and a "library" (you own the loop and call into it) hinges on this pattern.
- **Keep in mind**: The loop is hot code — it sits in the 10% of code where the program spends most of its time, so efficiency matters and bugs here have outsized impact. You may need to coordinate with the platform's event loop (e.g., on Windows use `PeekMessage()` to avoid blocking; in a browser you cannot write a classic loop and must use `requestAnimationFrame()`). A plain fixed-timestep loop with no sync runs at hardware-dependent speed; adding `sleep()` prevents running too fast but can't help if a frame overruns — the game just slows down. A variable (fluid) timestep adapts to both fast and slow hardware but makes the game non-deterministic and can destabilize physics (floating-point error accumulates differently across machines; physics damping is tuned to a specific step). You must decide who owns the loop (platform event loop / engine / yourself), how to manage power consumption (run flat-out vs. clamp frame rate and sleep), and how to control gameplay speed (fixed no-sync, fixed with sync, variable, or fixed-update-with-variable-rendering).
- **Application sketch**: Structure the loop as `processInput()` → `update()` → `render()`, never blocking on input. Track real elapsed time per frame. The recommended robust form uses a fixed update timestep with variable rendering: maintain a `lag` accumulator; each frame add elapsed real time to `lag`; run an inner `while (lag >= MS_PER_UPDATE)` loop calling `update()` with a fixed step (optionally bail after a max iteration count to avoid lockup); then `render()`. `MS_PER_UPDATE` is the simulation granularity (not the visible frame rate) — keep it short for fidelity but longer than the slowest machine's `update()` cost. To smooth motion, pass the residual `lag / MS_PER_UPDATE` (a 0..1 value) to `render()` so the renderer can interpolate/extrapolate between the previous and next simulation states, accepting that the extrapolation is a guess corrected next frame.

### Update Method
- **Intent**: Simulate a collection of independent objects by telling each to process one frame of behavior at a time.
- **Recognize the need**: An "increasingly large pile of variables and imperative code all stuffed in the game loop," each block handling one specific entity — code that's been "mushed" together; per-entity state (timers, direction flags, rate-of-fire counters) living as locals in the game loop rather than on the entities, making it hard to add more instances; entities hardcoded into the loop so adding/removing them requires editing the loop rather than populating from data; long-running behavioral loops (e.g., a patrolling skeleton's `for` loop) that lock up the program and block input/rendering; needing many entities to behave simultaneously and independently each frame.
- **Why it works**: Each entity encapsulates its own behavior behind an abstract `update()` method that processes one frame's worth of behavior. The game loop holds a collection of these objects without knowing their concrete types and, each frame, walks the collection calling `update()` on each. This decouples each object's behavior from the loop and from the other objects, so all entities appear to advance simultaneously while the loop stays uncluttered and entities can be added/removed (or loaded from data) freely.
- **When to use**: A wide swath of games with live actors the player interacts with (space marines, dragons, Martians, ghosts, athletes) use it. It fits when the game has a number of objects/systems that need to run simultaneously, each object's behavior is mostly independent of the others, and the objects need to be simulated over time. It is a poor fit for abstract games whose moving pieces are more like chess pieces than living actors (though per-frame animation may still benefit).
- **Keep in mind**: Splitting straight-line behavior into single-frame slices raises up-front complexity (the simple `for`-loop patrol becomes an `update()` with an explicit `patrollingLeft` state field); lightweight concurrency (generators, coroutines, fibers) or the Bytecode pattern can sometimes restore imperative flow. You must explicitly store enough state to resume where you left off each frame (the State pattern often helps), because the execution position is lost when `update()` returns. Objects simulate each frame but are not truly concurrent — the *order* of updates matters (A sees B's previous state; B sees A's new state), so the core is still turn-based with one-frame turns; if order-independence is required, combine with Double Buffer. Be careful modifying the object list while iterating: cache the count at loop start to skip newly added objects; walk the list backwards so removals only shift already-updated items; or defer removals by marking objects "dead," skipping dead objects during update, and sweeping them afterward. Putting `update()` on the main entity class via subclassing gets brittle at scale — prefer the Component pattern (update on components), or delegate via State/Type Object patterns with a non-virtual `update()` that forwards. For dormant/inactive objects, a single collection wastes time (and cache) skipping them; a separate active-only collection saves CPU but uses extra memory and must be kept in sync with the master collection.
- **Application sketch**: Define an abstract `Entity` (or component) with a virtual `update()` method (optionally taking an elapsed-time parameter for variable timesteps). Maintain a `World` holding a collection (array) of `Entity*`. Each frame the game loop iterates the collection and calls `update()` on each, caching the initial length so newly spawned objects don't act on their birth frame and walking backwards (or deferring removals) so deleted objects don't cause skips. Implement concrete behaviors by subclassing `Entity` (or attaching components) and moving per-entity state (patrol direction, fire timer) onto the entity as fields. To support variable timesteps, scale behavior by the passed-in elapsed time and guard against overshoot. Decide what class hosts `update()` (entity / component / delegate) and how to handle dormant objects (single collection with skip-flag vs. separate active collection).

## Behavioral Patterns

Patterns for defining and organizing *what* entities do.

### Bytecode
- **Intent**: Give behavior the flexibility of data by encoding it as instructions for a virtual machine.
- **Recognize the need**: Behavior hard-coded in the engine's implementation language, so every tweak forces an engineer into low-level code and a glacial recompile, killing the creative iteration loop; needing to update behavior after ship (patches, new content) but doing so means patching the executable; wanting modding/user-authored behavior, which would require shipping source and a compiler toolchain, and a buggy mod could crash another player's game; behavior that must be sandboxed away from the core engine for security/stability; an Interpreter pattern tried but its sprawling tree of tiny objects is too slow and memory-hungry (pointer chasing, cache misses, virtual calls); wanting behavior that is easy to modify, reload, and physically separate from the rest of the executable.
- **Why it works**: An instruction set of low-level operations is encoded as a dense, linear sequence of bytes and executed by a virtual machine one instruction at a time using a stack for intermediate values. Because the behavior lives in data interpreted by a VM you control, it can only reach the engine through the few primitives you defined — so it is sandboxed, reloadable, and faster than Interpreter's object trees. Composition emerges from the stack: instructions pop operands, do work, and push results, so deeply nested expressions flatten into a straight byte stream.
- **When to use**: When you have a lot of behavior to define and your game's implementation language is a poor fit because it is too low-level/tedious/error-prone, iterating takes too long due to slow compiles or tooling, or it has too much trust and you need to sandbox the behavior from the rest of the codebase. It is the most complex pattern in the book — don't throw it in lightly, and avoid it for performance-critical engine parts since bytecode is slower than native code.
- **Keep in mind**: It is seductive — little languages inevitably grow into ad-hoc full languages with the architectural elegance of a shanty town, so deliberately control scope. You will need a front-end: binary bytecode is not user-authorable, so you must build a compiler or authoring tool (graphical UIs can make invalid programs impossible and spare you a grammar/parser); if you can't resource that, this pattern isn't for you. You will miss your debugger — standard debuggers/analyzers target real languages, not your custom bytecode, so plan to invest in tooling to inspect what bytecode is doing, especially if the game is moddable.
- **Application sketch**: (1) Define an instruction set (an enum of operations) spanning external primitives that reach into the engine (setHealth, playSound, spawnParticles), internal primitives (literals, arithmetic, stack manipulation), control flow (jumps that mutate the instruction index), and abstraction (procedures via a return stack). (2) Encode each behavior as a sequence of bytes, one byte per instruction, stuffing literal values directly into the byte stream. (3) Build the VM as a loop with a switch over the current instruction, dispatching to the corresponding API method, backed by a value stack with push/pop. (4) Have instructions pop operands, act, and push results; add a LITERAL instruction that reads the next byte(s) as a value and pushes it. (5) Walk through stack states to verify composition (e.g., increase health by the average of agility and wisdom). (6) Build an authoring front-end (text compiler or, preferably for non-technical users, a graphical tool) that emits the bytecode.

### Subclass Sandbox
- **Intent**: Define behavior in a subclass using a set of operations provided by its base class.
- **Recognize the need**: A base class with many derived classes (e.g., a hundred superpower subclasses) and lots of redundant code across them (a freeze ray, heat ray, and mustard ray are mostly the same); every corner of the engine coupled to these derived classes because they poke into subsystems and layers never meant to be touched directly; changes to outside systems keep breaking random derived-class code, dragging graphics/audio programmers into gameplay; hard to define invariants all subclasses obey (e.g., all audio properly queued and prioritized) because each subclass calls into the sound engine on its own; each gameplay programmer needing a clean set of primitives instead of `#include`-ing random headers and nosing into the rest of the codebase.
- **Why it works**: The base class declares an abstract protected sandbox method (subclasses must override it) and several protected, typically non-virtual provided operations. Subclasses implement the sandbox method by calling only those provided operations. This centralizes coupling in the base class: the base is coupled to the game systems, but the many subclasses are coupled only to their base. Redundant code can be rolled up into new provided operations on the base, and the result is a shallow-but-wide hierarchy with a single point of leverage — love poured into the base class benefits all subclasses.
- **When to use**: When you have a base class with a number of derived classes, the base class can provide all the operations a derived class may need, there is behavioral overlap you want to share between subclasses, and you want to minimize coupling between those derived classes and the rest of the program. It is a very simple, common pattern — a non-virtual protected method laying around usually means you're already using something like it.
- **Keep in mind**: Base classes tend to accrete code, and this pattern is particularly susceptible to the brittle base class problem: the base ends up coupled to every system any derived class talks to, while subclasses are intimately tied to the base, making the base hard to change. The upside is that derived classes become cleanly isolated from the world. If the base class turns into a giant bowl of code stew, pull some provided operations out into separate classes (the Component pattern can help). Wide inheritance trees are easier to work with than deep ones.
- **Application sketch**: (1) Create a base class with an abstract protected sandbox method (e.g., `activate()`). (2) Add protected provided operations covering what subclasses need (e.g., `move()`, `playSound()`, `spawnParticles()`, plus state accessors like `getX()`/`getY()`). (3) Implement those operations in the base — this is where the base class couples to physics/audio/etc., encapsulating that coupling away from subclasses. (4) For each new behavior, create a subclass inheriting from the base, override the sandbox method, and implement its body by calling only the provided operations (arbitrary control flow is allowed). (5) When duplication appears across subclasses, roll it up into a new provided operation on the base. (6) Decide how many operations to provide (minimal vs. all — more operations decouple subclasses but bloat the base), whether to expose them directly or via helper objects (e.g., a `SoundPlayer` returned by a getter), and how the base obtains its state (constructor argument, two-stage initialization with `init()`, static state, or a Service Locator).

### Type Object
- **Intent**: Allow the flexible creation of new "classes" by creating a single class, each instance of which represents a different type of object.
- **Recognize the need**: Many "kinds" of things (e.g., hundreds of monster breeds) each modeled as a subclass, and you spend all day writing little seven-line subclasses and recompiling; designers constantly tune numbers (troll health 48 → 52) and you've become a data monkey — every tweak needs a code change, recompile, and check-in; designers want to create and tune breeds with no programmer intervention; you don't know what types you'll need up front (e.g., downloadable content adding new breeds); you want to add or modify types without recompiling or changing code; baking the kinds into the language's type system is too rigid.
- **Why it works**: Define a type object class and a typed object class; each type object instance represents a different logical type, and each typed object holds a reference to the type object describing its type. Instance-specific data lives in the typed object; data and behavior shared across all instances of the same conceptual type lives in the type object. Objects referencing the same type object behave as if they were the same type — like subclassing, but without a fixed set of hard-coded subclasses. This lifts part of the type system out of the code into runtime data, so new types are just new type object instances, typically loaded from a config file.
- **When to use**: Anytime you need to define a variety of different "kinds" of things but baking the kinds into your language's type system is too rigid. Especially when you don't know what types you will need up front (e.g., DLC adding new breeds), or you want to modify or add new types without recompiling or changing code.
- **Keep in mind**: Moving "type" from rigid code into flexible-but-less-behavioral objects loses some things. Type objects must be tracked manually — you are now responsible for instantiating and keeping breed objects in memory as long as typed objects need them; the compiler no longer does this bookkeeping. It is harder to define behavior per type: subclassing lets an override run arbitrary code, but Type Object replaces an overridden method with a member variable, so it is easy to define type-specific data but hard to define type-specific behavior. Workarounds include storing a function pointer that selects among a fixed set of predefined behaviors, or moving behavior fully into data via the Interpreter or Bytecode patterns.
- **Application sketch**: (1) Define a type object class (e.g., `Breed`) holding the shared data/behavior, such as starting health and the attack string. (2) Define a typed object class (e.g., `Monster`) that stores a reference to a type object; in its constructor it uses the breed to determine starting state, and it forwards shared queries like `getAttack()` to the breed. (3) Construct typed objects by giving them a reference to a type object instance, or add a factory "constructor" on the type object (e.g., `Breed::newMonster()`) to also control allocation (Object Pool, custom heap). (4) Author types from data (e.g., a JSON file) so new types need no code change. (5) Optionally add inheritance between type objects: give a breed a parent breed, let a child override specific attributes (non-zero health, non-null attack) and inherit the rest; implement either dynamically (walk the parent chain on each lookup) or via copy-down at construction (faster, discards the parent pointer). (6) Decide whether the type object is encapsulated or exposed, how typed objects are created, whether the type can change at runtime, and what inheritance (none/single/multiple) to support.

## Decoupling Patterns

Patterns that split components apart so they can change independently.

### Component
- **Intent**: Allow a single entity to span multiple domains without coupling the domains to each other.
- **Recognize the need**: A single class (e.g., `Bjorn`) ballooned into a multi-thousand-line dumping ground touching input, physics, graphics, and sound — a "Gordian knot" where every domain knows about the others, so any change requires understanding physics, graphics, and sound simultaneously; a class getting massive and hard to work with, with bugs accumulating faster than features; needing to define a variety of objects (decorations, props, zones) that share different capabilities, but inheritance forces you into the Deadly Diamond or pushes everything up into a base class that wastes memory on unused domains; needing to split a game across threads along domain boundaries (AI on one core, sound on another), where a single class with `UpdateSounds()` and `RenderGraphics()` methods called from different threads is begging for concurrency bugs.
- **Why it works**: The code for each domain is placed in its own component class, and the entity is reduced to a thin container that owns and delegates to those components. Because the components do not refer to each other directly (by default), a programmer working on physics can modify their component without knowing anything about graphics. Components also become reusable, plug-and-play packages: a decoration is a `GameObject` with a `GraphicsComponent` but no `PhysicsComponent`, a prop has both, so you build entities by selecting parts rather than weaving inheritance hierarchies.
- **When to use**: When you have a class that touches multiple domains which you want to keep decoupled from each other; when a class is getting massive and hard to work with; when you want to define a variety of objects that share different capabilities but inheritance doesn't let you pick the parts you want to reuse precisely enough. Most commonly found within the core class that defines game entities, but useful elsewhere too.
- **Keep in mind**: Adds a good bit of complexity over a simple class — each conceptual "object" becomes a cluster that must be instantiated, initialized, and correctly wired together; inter-component communication becomes more challenging; memory layout is more complex. Don't over-engineer a "solution" to a non-existent problem. You often hop through a level of indirection (get the component, then act) which can hurt performance-critical inner loops — though it can also *improve* performance and cache coherence by enabling the Data Locality pattern.
- **Application sketch**: Start from the monolithic `update()` and slice it along domain boundaries — pull input handling into `InputComponent`, physics into `PhysicsComponent` (moving both behavior *and* data like `Volume` out), graphics into `GraphicsComponent`; the entity keeps only the components plus shared "pan-domain" state (position, velocity) that components read and write to coordinate implicitly. Have `update()` delegate to each component in order. To enable reuse, hide each component behind an abstract base class and have the entity hold a pointer to the interface, so concrete implementations (e.g., `PlayerInputComponent` vs. `DemoInputComponent`) can be swapped at construction — taken to its extreme the entity becomes a generic `GameObject` component bag built by a factory. Decide how the object gets its components (self-created vs. externally provided) and how components communicate: by modifying shared container state (decoupled but order-dependent and memory-muddying), by direct references between paired components (simple, fast, but partially re-coupled), or by a messaging/mediator system on the container (most decoupled, most complex).

### Event Queue
- **Intent**: Decouple when a message or event is sent from when it is processed.
- **Recognize the need**: A synchronous API (e.g., `playSound()`) blocks the caller until the engine finishes, freezing the game for frames while a resource loads; requests cannot be processed in aggregate — the API sees each call through a pinhole, so two same-frame plays of the same sound stack to twice the loudness and the hardware limit gets blown with no prioritization; requests processed on the wrong thread — the synchronous API runs on the caller's thread, so calls from rendering, AI, etc. stomp over each other while a dedicated audio thread sits idle; a push model on the sender's side meeting a pull model on the receiver's side needing a buffer between them; wanting game systems (combat, tutorial) to communicate without being directly aware of each other.
- **Why it works**: A queue stores notifications or requests in FIFO order; sending a notification just enqueues the request and returns immediately, and the processor pulls items from the queue at a later, convenient time. This decouples the sender from the receiver both statically (they need not know each other) and in time. The queue hands control to the receiver — it can delay processing, aggregate or dedupe requests, or discard them — at the cost of taking that control away from the sender, who can only throw a request on the queue and hope for the best.
- **When to use**: When you want to decouple something *in time*. If you only want to decouple *who* receives a message from its sender, Observer or Command do it with less complexity — you only need a queue when there is a push/pull mismatch to buffer. A poor fit when the sender needs a response, since the sender can only enqueue and hope.
- **Keep in mind**: Event queues are complex and have wide-reaching architectural effect. A central event queue is a global variable in disguise — the protocol wraps the state, but the subtle-interdependency danger of globals remains. The state of the world can change under you: by the time an event ("entity died") is processed, the entity may be deallocated and nearby foes may have wandered off, so queued events must capture ephemeral details at send time and tend to be more data-heavy than synchronous notifications. You can get stuck in feedback loops (A sends, B responds by sending, A responds…); the asynchrony unwinds the stack so the game keeps running while spurious events slosh back and forth — a common rule is to avoid *sending* events from within code that is *handling* one. A little debug logging is recommended.
- **Application sketch**: Reify the request into a small message struct (e.g., `PlayMessage { id, volume }`). Store pending messages in a plain array — no dynamic allocation, no bookkeeping overhead, cache-friendly contiguous memory. `playSound()` writes a message at the tail and returns almost instantly; an `update()` method (called from the game loop or a dedicated thread) reads from the head and advances it. Upgrade the array to a ring buffer with explicit `head_` and `tail_` indices incremented modulo `MAX_PENDING` so neither shifting nor reallocation is needed, with an assertion guarding against the tail colliding with the head. Aggregate requests by scanning the queue at enqueue time and merging duplicates (collapsing to the loudest). To span threads, make `playSound()` and `update()` thread-safe (a short lock around the small enqueue work; a condition variable in `update()` so it doesn't burn CPU while idle). Decide what goes in the queue (events describing the past, often broadcast, vs. messages/requests for the future, usually single-cast), who can read (single-cast / broadcast / work queue), who can write (one-to-one through many-to-many), and the lifetime/ownership of queued objects (pass ownership, share ownership, or queue-owns-it via an object pool).

### Service Locator
- **Intent**: Provide a global point of access to a service without coupling users to the concrete class that implements it.
- **Recognize the need**: Many corners of the codebase (physics for a falling rock, AI for a sniper, UI for a menu beep) all need to call into a system like audio, and every call site is hard-coupled to a concrete `AudioSystem` class plus its access mechanism (static class or singleton); changing or moving the implementation means updating every call site — "giving a hundred strangers directions to your house" and re-telling them when you move; wanting to swap implementations (console audio, a disabled/null audio, a logging decorator) without touching callers; the facility is fundamentally singular (one audio device, one display) and plumbing it through ten layers of methods just so one deeply nested call can reach it is needless complexity; wanting to temporarily disable a system during development without ripping out call sites.
- **Why it works**: A service class defines an abstract interface to a set of operations; a concrete service provider implements that interface; a separate service locator provides access by finding an appropriate provider while hiding both the provider's concrete type and the process used to locate it. Callers ask the locator for the service and get back the abstract interface, so only the one piece of initialization code that registers the provider knows the concrete class. The service interface itself is unaware it is being accessed through a locator, so the pattern can be applied to existing classes not designed around it (unlike Singleton, which affects the service class's own design).
- **When to use**: Sparingly. First consider *passing* the object to the code that needs it — that is dead simple and makes the coupling obvious, and it covers most needs. Reach for a locator only when manually passing the object is gratuitous or actively obscures code: systems like logging or memory management that shouldn't be part of a module's public API (rendering parameters should be about rendering, not logging), or facilities that are fundamentally singular in nature (one audio device, one display) and are ambient properties of the environment. In those cases it acts as a more flexible, more configurable cousin of Singleton.
- **Keep in mind**: The core difficulty is that it takes a dependency and defers wiring it to runtime — you gain flexibility but it becomes harder to understand your dependencies by reading the code. The service actually has to be located, so you must handle the case where location fails (the book recommends a null service). The service doesn't know who is locating it: because any code anywhere can request and then poke at it, the service must work correctly in every circumstance — a class that expects to be used only during the simulation phase of the loop, say, is not safe to expose as a service. Used poorly, it carries all the baggage of Singleton with worse runtime performance. There is also temporal coupling: some outside code must register the provider before any caller asks for it.
- **Application sketch**: Define the abstract service interface (e.g., `Audio` with `playSound()`, `stopSound()`, `stopAllSounds()`). Implement a concrete provider (`ConsoleAudio`) that does the real work. Create a `Locator` class with a static `getAudio()` accessor and a `provide(Audio*)` registration method; `getAudio()` returns the registered pointer (often inlined, near-zero cost). At startup, call `Locator::provide(new ConsoleAudio())`; calling code then uses `Locator::getAudio().playSound(...)` knowing only the abstract interface. To eliminate the missing-service failure mode, define a `NullAudio` provider that implements the interface with no-op bodies (the Null Object pattern), default the locator to it in `initialize()`, and check for `NULL` inside `provide()` so `getAudio()` can return by reference and always yields a valid object — this also lets you intentionally disable a system by simply not registering a real provider. For selective logging, wrap a provider in a `LoggedAudio` Decorator that forwards calls to an inner provider while logging them, and register the decorator instead. Decide how the service is located (outside registration, compile-time binding via preprocessor macros, or runtime configuration with reflection), what happens on failure (let the caller handle a `NULL`, halt with an assertion, or return a null service), and the scope of access (global, or restricted to a class and its descendants for domain-local services like networking).

## Optimization Patterns

Patterns for making it faster — apply only with a measured problem.

### Data Locality
- **Intent**: Accelerate memory access by arranging data to take advantage of CPU caching.
- **Recognize the need**: A performance-critical loop iterating over an array of pointers to objects (pointer chasing), with each dereference likely causing a cache miss; game entities decomposed into components accessed via pointer hops (entity pointer → component pointer → update), multiplying misses per element; heap objects scattered randomly across address space after repeated allocation/free, defeating locality; hot loops bristling with `->` indirection operators you could remove; virtual method calls forcing vtable lookups (more pointer chasing) in inner loops; a particle/object array littered with inactive elements you skip past, wasting every cache line loaded between useful work; a per-frame-updated structure carrying rarely used fields (e.g., loot-drop data on an AI component) that bloat each element and reduce how many fit in a cache line.
- **Why it works**: Modern CPUs don't fetch bytes one at a time — reading any byte pulls a whole cache line (around 64–128 bytes) of contiguous memory into fast on-chip cache. If the next byte needed is already on that line, it's a cheap cache hit; otherwise the CPU stalls for hundreds of cycles on a cache miss. By laying out data contiguously in the order it's processed, each fetch drags in the data that's about to be used next, turning a whirlwind tour of main memory into a straight crawl through a packed array.
- **When to use**: Only when you have a confirmed performance problem and have verified (with a cache profiler such as Cachegrind) that cache misses are the cause — slow code from other causes won't benefit. Don't waste effort on infrequently executed code; the result is invariably more complex and less flexible. Throughout design, do think about cache-friendliness of data structures, but avoid pre-emptive major surgery.
- **Keep in mind**: Pleasing this pattern means sacrificing abstraction — interfaces, inheritance, and virtual methods all imply pointer/reference access and vtable hops, which cause the very cache misses you're trying to avoid. There's no silver bullet, only trade-offs between flexibility and speed. On multi-threaded code, the locality assumption flips: threads modifying nearby data on the same cache line trigger costly cache synchronization, so per-thread data may want to live on separate lines.
- **Application sketch**: Three techniques from the chapter. (1) Contiguous arrays — replace an array of pointers-to-entities (each pointing to components) with one flat, homogenous array per component type (AI array, physics array, render array) holding the actual data, not pointers; the game loop walks each array directly. (2) Packed data — keep active objects contiguous at the front of the array tracked by a `numActive_` counter; on activate, swap the particle with the first inactive one; on deactivate, swap with the last active one; the active flag can then be dropped entirely since position implies state. (3) Hot/cold splitting — break a structure into a hot piece (state touched every frame) and a cold piece (rarely used state such as loot-drop info), with the hot piece holding a pointer to the cold (or use parallel arrays indexed identically) so cold data isn't dragged into the cache each frame.

### Dirty Flag
- **Intent**: Avoid unnecessary work by deferring it until the result is needed.
- **Recognize the need**: Derived data (e.g., world transforms in a scene graph) recomputed every frame even when the primary data hasn't changed; eager recalculation on every primary change causing redundant work — moving four ancestors in one frame recomputes a child's world transform four times when only the final result is rendered; hierarchical or cascading dependencies turning one local change into many recomputations; static or rarely changing data processed repeatedly on a hot path; derived data expensive to compute but only actually consumed at well-defined moments (rendering, saving); paying for results that are sometimes never used before being invalidated again.
- **Why it works**: The pattern decouples changing primary data from updating the derived data. A single bit tracks whether the derived data is out of sync. Setting the flag on a primary change is cheap (a couple of assignments, no recursion). When the derived data is finally needed, the flag is checked; if set, the expensive process runs once and the flag clears, otherwise the cached result is reused. This collapses multiple primary changes along a chain into a single recalculation and skips unchanged objects entirely.
- **When to use**: Only for a specific, measured performance problem that justifies the added complexity. Applies to two kinds of work — calculation (slow math) and synchronization (pushing data elsewhere, to disk or over the network). Two requirements must hold: the primary data changes more often than the derived data is used (otherwise deferral saves nothing), and the derived data should be hard to update incrementally (if a cheap running total is possible, prefer that over recalculating from scratch on demand).
- **Keep in mind**: Deferring too long is risky — when the result is needed, it's usually needed *now*, and a slow calculation causes a visible pause; worse, if something fails before the sync point, the work may never happen (unsaved document lost on power loss). You must set the flag *every* time any primary state changes, or stale derived data produces subtle bugs; encapsulate modifications behind a narrow API so the flag can't be missed. You must also keep the previous derived data in memory, trading memory for speed — worthwhile when calculation is slow and memory is cheap, but not when memory is the tighter resource.
- **Application sketch**: Add to each node a cached `world_` field and a `dirty_` flag initialized `true` (a brand-new node's world transform is unknown). In `setTransform()`, update the local transform and set `dirty_ = true`, but do *not* recursively mark children. During the traverse that consumes the derived data (e.g., `render(parentWorld, parentDirty)`), pass a `dirty` parameter that is true if any ancestor was dirty; if `dirty_ || parentDirty`, recompute `world_ = local_.combine(parentWorld)` and clear `dirty_`, otherwise reuse the cached `world_`. The descend recurses with the pre-clear combined dirty state (`dirty_ || parentDirty`) as the new parent-dirty. Decide separately when flags are cleaned (on demand, at well-defined checkpoints, or via a background timer) and the granularity of tracking (fine-grained per-element flags process only what changed; coarse-grained flags use less memory and less per-chunk overhead but reprocess some unchanged data).

### Object Pool
- **Intent**: Improve performance and memory use by reusing objects from a fixed pool instead of allocating and freeing them individually.
- **Recognize the need**: Objects (particles, sounds, entities) created and destroyed frequently each frame; heap fragmentation a real risk — free space shattered into small pieces so a large allocation fails even though total free memory suffices; per-object heap allocation/deallocation slow; soak tests (multi-day demo runs required by console makers) crashing due to creeping fragmentation; objects similar in size; objects wrapping expensive-to-acquire resources (database or network connections) that could be reused instead of re-acquired.
- **Why it works**: The pool allocates one large contiguous block up front and never frees it during play, so the memory manager sees no churn and no fragmentation accumulates. To callers, it exposes a `create`/reuse interface: find a free object, mark it in use, return it; on release, mark it not in use. Because objects are recycled rather than allocated, creation and destruction cost no heap traffic.
- **When to use**: When you need to frequently create and destroy objects, objects are similar in size, heap allocation is slow or leads to fragmentation, or each object encapsulates a resource that is expensive to acquire and could be reused. Common for game entities, visual effects, and currently playing sounds.
- **Keep in mind**: The pool may waste memory on unneeded object slots if sized too large (too small is obvious — a crash). Only a fixed number of objects can be active at once; pick an overflow strategy: prevent outright by tuning sizes, skip creating the new object (fine for particles when the screen is already full), forcibly kill an existing object (good for sounds where the new one masks the cutoff), or grow the pool at runtime. Slot size is fixed, so mixed-type pools must size slots for the largest object, wasting memory on small ones — consider separate pools per size. Reused objects aren't automatically cleared by the memory manager's debug magic values, so uninitialized-field bugs become invisible; fully initialize on reuse and consider clearing slots on reclaim. With a garbage collector, pooled-but-unused objects still occupy memory and may hold references that block collection — clear those references on release.
- **Application sketch**: Define a pool class holding a fixed-size array of objects, each exposing an `inUse()` query (which can reuse existing state like a `framesLeft_` countdown rather than a separate flag). `create()` scans for the first not-in-use object, initializes it, and returns it (returning `NULL` or applying an overflow strategy if none free). An `animate()`/update method iterates every object each frame, updating active ones and deactivating those whose lifetime expired. To remove the O(n) scan in `create`, use a *free list*: store a union on each object holding either its live state or a `next` pointer to the next free object, threading a singly linked list through the dead objects' own memory; the pool keeps a head pointer. Creation pops the head (O(1)); deactivation pushes the object back onto the list (O(1)). Decide whether objects are coupled to the pool (simpler, can enforce pool-only construction, may skip a separate in-use flag) or generic (any type poolable, in-use tracked externally in a bit field), and whether the pool reinitializes objects internally (full encapsulation, but the pool's interface must mirror every initializer) or returns a reference for outside code to initialize (simpler pool interface, but caller must handle `NULL`).

### Spatial Partition
- **Intent**: Efficiently locate objects by storing them in a data structure organized by their positions.
- **Recognize the need**: A doubly nested loop comparing every pair of objects each frame, giving O(n²) proximity tests that spiral out of control as object count grows; the engine frequently asking "what objects are near this location?" and that query being a bottleneck; objects living in an unordered array so any near-query must scan the entire array; combat, collision, audio falloff, or chat-radius checks scaling quadratically with population; enough location queries that performance is genuinely suffering.
- **Why it works**: Sorting or bucketing objects by position turns a global scan into a local one. A query only inspects the partition(s) overlapping the region of interest, so the work depends on how many objects are *nearby*, not on the total count. In the chapter's grid example, partitioning the battlefield into cells reduces an O(n²) all-pairs test to many small per-cell tests, and the outer loop over cells is cheaper than the inner loops it replaces. Updating the structure when an object moves keeps the index correct for the next query.
- **When to use**: When you have a set of objects each holding a position and you perform enough location queries that performance suffers. Used for both moving game objects and static art/geometry; sophisticated games keep multiple partitions for different content kinds.
- **Keep in mind**: The payoff grows with object count — with small *n*, the bookkeeping isn't worth it. Because the structure is organized by position, *moving* objects are expensive: every position change may require removing the object from one partition and inserting into another, which adds code complexity and CPU cycles (like a hash table whose keys change spontaneously). The partition also consumes extra memory for its bookkeeping structures; it trades memory for speed, which is a losing proposition when memory is tighter than cycles.
- **Application sketch**: The chapter's reference implementation is a fixed grid. Overlay the world with fixed-size cells; each cell stores a linked list of the objects whose positions fall inside it. Give each object a position, a back-pointer to the grid, and `next`/`prev` pointers so cells hold doubly linked lists (fast insert/remove). On creation or `add(unit)`, compute the cell index by dividing world coordinates by the cell size and truncating, then splice the unit onto the front of that cell's list. To answer proximity queries, walk each cell and compare pairs only within that cell; for non-zero attack radii, also compare against (half of) the neighboring cells to avoid double-counting pairs. On `move(unit, x, y)`, if the new position crosses a cell boundary, unlink the unit from its old cell's list and re-`add` it to the new cell; otherwise just update the position. Beyond the grid, choose among design axes: flat (simpler, constant memory, faster moves) vs. hierarchical (handles empty space and dense clusters better); object-independent partitioning (incremental add/move, possibly imbalanced) vs. object-dependent such as BSPs/k-d trees/BVHs (balanced, consistent query times, best for static geometry); and storing objects only in the partition (one collection, no sync) vs. keeping a second flat collection for fast full traversal of all objects.
