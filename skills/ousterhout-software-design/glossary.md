# Glossary — *A Philosophy of Software Design*

**Abstraction** - a simplified view of an entity that omits unimportant details; a module's interface is its abstraction. Omits important details → *false abstraction*. (Ch 4)
**Aggregation (exception)** - handling many distinct exceptions with one handler, usually high up; replaces many special-purpose handlers with one general mechanism. (Ch 10)
**Agile development** - incremental/iterative process; matches this book, but risks tactical, feature-focused sprawl. (Ch 1, 19)
**Change amplification** - symptom of complexity: a simple change requires edits in many places. (Ch 2)
**Classitis** - over-decomposition into many shallow classes; the false belief that more/smaller is always better. (Ch 4)
**Cognitive load** - symptom of complexity: how much a developer must know to complete a task. (Ch 2)
**Complexity** - anything making a system hard to understand and modify; caused by dependencies and obscurity; weighted by developer time C = Σ(cₚ·tₚ). (Ch 2)
**Composition** - building classes from small helper classes instead of implementation inheritance; preferred for sharing functionality. (Ch 19)
**Configuration parameter** - an exported value controlling module behavior; often punted complexity; prefer auto-computation + defaults. (Ch 8)
**Conjoined methods** - two methods so interdependent you can't understand one without the other; the split was wrong. (Ch 9)
**Consistency** - similar things done similarly, dissimilar differently; creates cognitive leverage. (Ch 17)
**Context object** - one object holding all system-global state, referenced via constructors; the least-bad fix for pass-through variables. (Ch 7)
**Critical path** - the minimal code executed in the most common case; design hot code around it. (Ch 20)
**Cross-module design decision** - a decision affecting multiple modules (e.g. a protocol); document once, reference elsewhere. (Ch 13)
**Decorator** - a wrapper extending an object with a similar API; tends to be shallow and pass-through-heavy; easy to overuse. (Ch 7)
**Deep module** - much functionality behind a simple interface (a "tall rectangle"). (Ch 4)
**Defaults** - values the module supplies automatically so callers needn't know them; "do the right thing without being asked." (Ch 5)
**Dependency** - a cause of complexity: code that can't be understood/modified in isolation. (Ch 2)
**Design it twice** - for each major decision, sketch ≥2 radically different alternatives and compare. (Ch 11)
**Design patterns** - accepted solutions to common problems; good when they fit, harmful when forced. (Ch 19)
**designNotes file** - a central file holding cross-module documentation, referenced by short pointer comments. (Ch 13)
**Device driver** - a low-level module implementing a general interface for a specific device; pushes specialization downward. (Ch 6)
**Dispatcher** - a method that selects among same-signature methods; legitimate interface duplication. (Ch 7)
**"Do the right thing"** - modules should act correctly without being explicitly asked (e.g. default buffering). (Ch 5)
**Exception** - any uncommon condition altering normal control flow; a major source of complexity. (Ch 10)
**False abstraction** - an interface that looks simple by omitting details callers actually need → obscurity. (Ch 4, 6)
**Fence** - a marker in an undo history list separating groups of related actions. (Ch 6)
**General-purpose module** - functionality for current needs, interface not tied to them; "somewhat" general is the sweet spot. (Ch 6)
**Generic container** - `Pair`/`std::pair`-style grouping with meaningless element names; obscures meaning. (Ch 18)
**Getter/setter** - accessors exposing instance variables; shallow, violate information hiding. (Ch 19)
**Implementation** - the code carrying out an interface's promises. (Ch 4)
**Implementation inheritance** - parent provides default implementations subclasses override; creates parent/subclass dependencies; use cautiously. (Ch 19)
**Information hiding** - encapsulating design decisions in a module so they don't appear in its interface (Parnas). (Ch 5)
**Information leakage** - a design decision reflected in multiple modules; a top red flag, often invisible. (Ch 5)
**Interface** - everything a caller must know to use a module; has formal (code) and informal (comments) parts. (Ch 4)
**Interface inheritance** - parent defines signatures, subclasses implement; reuses one interface → deeper abstraction. (Ch 19)
**Invariant** - a property always true of a variable/structure; reduces special cases and aids reasoning. (Ch 17)
**Investment mindset** - spending extra time now on design for long-term payoff. (Ch 3)
**Leverage** - a decision/invariant that solves or clarifies many problems at once. (Ch 21)
**Masking (exception)** - detecting and handling an exception at a low level so higher levels never see it. (Ch 10)
**Micro-benchmark** - a tiny program measuring one operation's cost. (Ch 20)
**Modular design** - decomposing a system into relatively independent modules, each with interface + implementation. (Ch 4)
**Obscurity** - a cause of complexity: important information not obvious. (Ch 2)
**Obvious code** - readable quickly with correct first guesses; the positive opposite of cognitive load and unknown unknowns. (Ch 2, 18)
**Overexposure** - an API forcing awareness of rare features to use common ones. (Ch 5)
**Pass-through method** - forwards args to a similar signature, adding nothing; signals confused responsibility. (Ch 7)
**Pass-through variable** - a value threaded through methods that don't use it. (Ch 7)
**Pull complexity downward** - absorb unavoidable complexity into a module rather than pushing it onto callers. (Ch 8)
**Red flag** - a sign a piece of code is more complex than it needs to be. (Ch 1)
**Repetition** - the same nontrivial code repeated; you haven't found the right abstraction. (Ch 9)
**Shallow module** - complex interface, little functionality; hides little. (Ch 4)
**Special case** - a condition requiring extra handling; design the normal case to handle edges for free. (Ch 6)
**Special-General mixture** - special-purpose code polluting a general mechanism. (Ch 9)
**Strategic programming** - investing continually in clean design; your primary goal is a great design that also works. (Ch 3)
**Tactical programming** - "get it working now"; accumulates complexity. (Ch 3)
**Tactical tornado** - a prolific, fast, purely tactical developer who leaves wreckage. (Ch 3)
**Technical debt** - borrowing time from the future; mostly never repaid. (Ch 3)
**Temporal decomposition** - structuring modules by execution order rather than knowledge; causes leakage. (Ch 5)
**Test-driven development** - writing unit tests before code; risks tactical, feature-focused design. (Ch 19)
**Unknown unknowns** - the worst symptom of complexity: not obvious what to modify or what info you need. (Ch 2)
**Waterfall model** - design-all-up-front; rarely works for software. (Ch 1)
**Zero tolerance** - refusing even small complexity additions, since complexity is incremental. (Ch 2, 3)
